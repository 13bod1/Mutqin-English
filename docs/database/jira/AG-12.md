## Technical Scope & Access Layer Boundaries
- Persistence logic for user accounts, session tokens (`refresh_tokens`), and phone verification codes (`auth_otps`).
- Scope boundary: Delivers database models and adapter query methods; does NOT implement live WhatsApp delivery gateways, SMS provider webhooks, or JWT issuance.
- Egyptian phone validation against local format (`^01[0125][0-9]{8}$`); E.164 format normalization is not implemented at the database layer.

## Proposed Acceptance Criteria (BDD / Gherkin)

### Scenario (Nominal): Egyptian phone formatting and OTP record persistence
```gherkin
Given a valid synthetic 11-digit Egyptian mobile number matching the local regex
When persisting identity and OTP generation records in "users" and "auth_otps"
```

### Scenario (Edge): Invalid phone format and expired OTP rejection
```gherkin
Given an invalid phone string or expired OTP verification code
When OTP verification query executes against "auth_otps"
Then access layer rejects invalid phone format and rejects expired OTP tokens on verification query.
```

## Known Disclosures & Invariant Policies
1. **Password Hash Verification Boundary:** The data access layer performs a string length check (`len >= 20`). Cryptographic hash validation (e.g. Argon2id or bcrypt hash structure verification) is an **application and crypto service tier responsibility**, not an automatic standalone database engine vulnerability.
2. **No Live Gateway:** External WhatsApp messaging and live OTP SMS dispatch are not integrated.
3. **Runtime Verification Evidence:** Verified via standalone legacy database test suite (105 tests on in-memory SQLite) and PostgreSQL 16.6 runtime probes (14/14 probes passed on portable PG 16.6, port 5433). Docker and production unverified. Baselines kept strictly separate. See [evidence/pg-runtime-summary.md](./evidence/pg-runtime-summary.md).
